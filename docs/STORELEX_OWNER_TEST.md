# Storelex owner-only live UPI test

This is a **real order / real payment attempt**, NOT a sandbox. No customer can access it; only numeric `BOSS_ID`/`BOSS_IDS` in private Telegram chat. Owner Pay now activates without new variables: it uses existing `DATA_DIR`, the Docker `/app/data` directory, or a local `data` directory. `STORELEX_OWNER_PAY_TEST=0` remains an emergency kill switch. A dedicated mounted volume is still strongly preferred; without one the placement journal can disappear on redeploy. Recent Storelex orders are checked before placement as an additional guard, but cannot guarantee protection against an unfinished/unknown placement after restart. `/status` and the bill show Pay availability. Run one bot instance. Never test with a real customer order without consent.

Owner can paste a Swiggy address link and group-cart link as ordinary messages, in either order or together. The bot picks a usable Storelex account (preferring zero-order) unless `/account <mobile>` explicitly selects one; it shows the last four digits, parses the address, imports the cart, and returns the bill automatically. Inspect it against Storelex UI and tap **Confirm bill & Pay ₹...** (or use `/pay <exact rupee payable>`). This is a single confirm+pay operation. `/whoami` shows the Telegram numeric ID if `BOSS_ID` does not match. Only a unique final `To Pay`, `Total Payable`, or `Grand Total` line explicitly formatted as `₹...` matching the entered amount allows the request. Other formats fail closed. The bill step calls Storelex best_coupon (auto-apply), then rereads the cart; only a coupon actually present in the fresh provider bill is marked verified. Storelex may return a plain numeric To Pay (e.g. `365`) instead of `₹365`; both are accepted as rupee values for the owner Pay button. If Storelex does not confirm it, the bill explicitly says coupon unverified. The provider may create a real order; if successful and it returns a UPI intent, the bot sends the provider-only QR. QR sent != paid. `/paystatus` reads Storelex payment status for the current cart; only `PAID` from the provider is confirmed. `/receipt` reads Storelex order_detail to show actual restaurant, items, bill lines, delivery details and tracking to the owner only; missing fields are omitted. `/track` checks Storelex order_status and only shares an actual HTTPS Swiggy tracking link; after QR, the bot also polls for a link every 30 seconds for up to 20 minutes (or until terminal status). A restart ends the in-memory poll; use `/track` while the same cart draft exists. Unknown/unavailable results must be checked manually. Unknown/timeout/amount_changed responses block retries; never retry `/pay` on the same cart. A private on-disk exclusive-create journal keyed by account+cart id blocks double placement across restarts; preserve it during deploys. New cart IDs are not automatically guaranteed safe against duplicate real orders—reconcile the first attempt before a new cart. The bot never asks for card/CVV.

Do not enable for all users after one successful test: payment status, settlement, order tracking, concurrency, durability and response variants must be separately validated. No public rollout switch is implemented. Never paste the access key into chat; rotate a key exposed in attached example docs.
